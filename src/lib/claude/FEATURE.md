# Claude lib — card generation contracts

The claude lib converts HTML content into Anki flashcards using the Anthropic API. Two mechanisms enforce the minimum-information principle:

**Prompt enforcement** (`SYSTEM_PROMPT` in `ClaudeService.ts`): Claude is instructed to produce one fact per card. Multi-fact paragraphs must be split into separate cards at extraction time. Tables of N rows produce N cards. Cloze cards are exempt (already single-fact by nature). If `userInstructions` explicitly requests detailed or longer cards, those instructions override the min-info default.

**No post-parse splitter.** There used to be one (`splitOversizedCards.ts`): it broke any non-cloze answer over 600 plain-text characters into up to 3 fragments along sentence boundaries. It was removed because it was net-destructive. Every fragment reused the original card's front, so `dedupeCardsByFront` — which runs inside `mergeDeckInfoArrays` and keys on the normalized front — kept only the first and silently discarded the rest. A 1869-character answer reached the user as 594 characters; without the splitter the same card ships whole. The splitter also stripped the answer's HTML before splitting and clamped output at 3 fragments, so even working as designed it dropped formatting and anything past ~1800 characters. Card length is now governed by the prompt alone (see Prompt enforcement above and the card-size suffix), which is where the decision belongs. Do not reintroduce a post-parse splitter without making the fragments survive dedupe — `longAnswerPreservation.test.ts` guards this.

**Parse hardening:** `parseDeckResponse` applies two extraction steps before `JSON.parse`. First, a line-anchored fence regex (`/^```json\n?|^```\n?|```\s*$/gm`) strips code fences from line boundaries only — backticks inside JSON string values are never touched. Second, `extractJsonArray(text)` locates the first `[` and last `]` and returns the slice, so leading/trailing prose cannot prevent parsing. When `JSON.parse` fails, `tryRepairDeckArray` runs `escapeStrayControlChars` then `jsonrepair`: `escapeStrayControlChars` converts every C0 control char except `\t \n \r` (0x00-0x08, 0x0b, 0x0c, 0x0e-0x1f) into a `\uXXXX` escape. This matters because `jsonrepair` itself **throws** on a raw stray control char inside a string (the German-law-PDF prod failure: PDF text extraction injects BEL/VT/ESC/US bytes into card text, so both `JSON.parse` and the repairer died and the job failed with `claude_parse_failed`). German „quotes", unescaped ASCII quotes, literal newlines/tabs, and trailing prose are all already handled by `jsonrepair` once the stray control chars are escaped. When `JSON.parse` **and** the repair both fail and the response is not an empty-content refusal, `parseDeckResponse` throws `ClaudeLargeSectionError` (`.message === LARGE_SECTION_USER_MESSAGE`, `.name === 'ClaudeLargeSectionError'`, exported) — a large or multi-chunk response Claude answered in good faith but `jsonrepair` could not salvage (the recurring `jsonrepair-threw` prod shape). The user is told to convert a smaller part or split the page instead of seeing `claude_parse_failed`. `UploadService` classifies it as an expected user-input state and `jobFailureReasonFromError` returns its message, so the actionable text reaches the user on both the upload and the `performConversion` job paths. The narrower `ClaudeParseError` (`.message === 'claude_parse_failed'`, `.name === 'ClaudeParseError'`) now only fires when `JSON.parse` succeeds but yields valid JSON that is not a deck array. Note: `max_tokens` truncation never reaches this branch — `generateDeckInfoFromChunk` throws `ClaudeTruncatedError` before parsing (see Truncated chunk retry), so `stop_reason` is never `max_tokens` here. Either way the raw payload never appears in the thrown error. The redacted summary log (`[Claude] Failed to parse response as JSON`) uses `redactClaudePayload(text)` which emits `{ length, prefix (80 chars), sha256_prefix (12 hex) }`, plus `repairFailureReason` (from the exported `describeRepairFailure(toParse)` — `jsonrepair-threw` | `not-array` | `empty-array` | `no-usable-card` | `recoverable`) and `rawTail` (last 400 chars, so a `max_tokens` truncation shows its cut point even when the full-body dump is display-truncated). On unrecoverable failure a second line `[Claude] Unrecoverable parse failure — full response` logs the **full raw body** (`{ chunkIndex, raw }`) so the next occurrence is reproducible — the body is study content, never API keys/tokens.

**Shape sanitization:** after a successful parse, `parseDeckResponse` runs the array through `sanitizeCompactDecks` instead of a blind `as CompactDeck[]` cast. Entries that are not objects with a `cards` array are dropped; cards whose `q` is missing, non-string, or blank are dropped individually (a card with no front is unusable, and `cheerio.load(undefined)` in `expandCompactDeckInfo` used to throw and fail the WHOLE chunk via `runFloorV1`'s per-chunk rejection — the 2026-07-26 `chunkIndex: 52` prod failure, issue #3850); `a` coerces to `''` when non-string, `tags`/`media` keep only string entries, a blank/missing deck name falls back to `Untitled deck`. Dropped counts log once per chunk as `[Claude] Dropped malformed entries from parsed response`. One malformed card now costs that card only, never its chunk.

**PDF-image-fallback bypass (multimodal path):** A PDF whose text layer is not machine-extractable falls back in `PrepareDeck.ts` to `convertPDFToImages`, producing HTML that is one `<img>` per page and zero text — indistinguishable from a genuinely blank screenshot to `isImageOnlyContent`, which wrongly rejected these dense-but-unextractable study PDFs before Claude's vision was ever tried (issue #3804). `PrepareDeck` now marks every `convertPDFToImages`-derived HTML with `imageFallback` and passes `options.pdfImageFallback = { mediaBaseDir: workspace.location }` to `generateDeckInfo`. When that option is set, `generateDeckInfo` **skips** `isImageOnlyContent` and delegates to `generateDeckInfoFromPdfImages` (in `generateDeckInfoFromPdfImages.ts`), which resolves each page's `<img src>` against the base dir (rejecting any path that escapes it, per CWE-22), reads the bytes, and sends each page to Claude's multimodal `messages.create` with `buildPdfPageVisionPrompt` — the same image-input shape `PhotoToFlashcardsUseCase` uses. Pages run at concurrency 4, each retrying once at a larger token budget on `max_tokens`. Cards are parsed with the shared `parseDeckResponse`, expanded via `expandCompactDeckInfo`, and merged with `mergeDeckInfoArrays` (both now exported). A page that returns no cards is skipped, and a page whose vision call fails terminally is skipped the same way — the failure is caught inside the worker rather than rejecting the shared `Promise.all`, so one bad page on a 68-page scan no longer discards the 67 that converted. The page's error is re-thrown only when **every** page failed, which keeps an outage reported as an outage instead of as empty content. When every page yields zero cards (genuinely blank) it throws `Error(EMPTY_CONTENT_USER_MESSAGE)`, so the blank-screenshot rejection now comes from Claude's own vision response, not a pre-call heuristic. The image-only fail-fast still fires normally for real image-only uploads (no `pdfImageFallback` flag). **Cost note:** one vision call per PDF page (2–30s each), so a rasterized-PDF conversion is materially more expensive than the text path; the fallback only triggers when text extraction already failed. Prompt caching does not apply to the per-page image payloads.

**Empty-content refusal classifier:** when the model returns prose instead of JSON because the page had no extractable text (layout-only Notion pages that are not image-only), `looksLikeEmptyContentExplanation(cleaned)` matches the refusal against `EMPTY_CONTENT_SIGNALS` and `parseDeckResponse` throws `Error(EMPTY_CONTENT_USER_MESSAGE)` instead of the generic `ClaudeParseError`, so the user is told the page looks empty rather than seeing `claude_parse_failed`. The signal list covers both self-descriptions ("no actual content", "consists only of") and direct requests for input ("I need to see", "please provide the", "no content was provided") — the latter added after prod showed these refusals falling through to a generic error.

**Observability:** `parseDeckResponse` uses `extractJsonArray` to locate the array; trailing prose is stripped and logged as `[Claude] Trailing prose stripped` with `chunkIndex`, `strippedBytes`, and an 80-char sample — grep this to track model drift. Parse failures are logged as `[Claude] Failed to parse response as JSON` with `chunkIndex` and three redacted payload shapes (no raw content); the leading-indicator metric is the count of this log line in pm2 stderr.

**Override path:** `userInstructions` passed to `generateDeckInfo` flow into the prompt as an "Additional instructions" block. A user asking for "keep cards detailed" or similar will get the prompt's min-info rules deprioritised in Claude's output, and nothing downstream shortens the result.

**Tag normalization:** `normalizeTag(raw: string): string` (exported) converts a raw tag string from Claude's response into a safe Anki tag: lowercase, spaces→`_`, non-`[a-z0-9_]` characters stripped, capped at 32 characters. Called in `expandCompactDeckInfo` (Claude-text path) and in `buildDeckInfo` inside `PhotoToFlashcardsUseCase` (Photo-to-Deck path). Empty tags (e.g. all-punctuation input) are filtered out before the card is written. The `SYSTEM_PROMPT` already declares `"tags": string[]` in the schema; `expandCompactDeckInfo` now normalizes every tag the model emits and drops empty results.

**Math delimiter contract:** `ANKI_MATH_FRAGMENT` (exported from `ankiMathFragment.ts`) is a short instruction block injected into every Claude prompt that may produce math content. It instructs Claude to use `\(...\)` for inline math and `\[...\]` for display math, never `$...$` or `$$...$$`. Chemistry uses `\(\ce{...}\)` via mhchem. The fragment is shared across `SYSTEM_PROMPT` (exported from `ClaudeService.ts`), `buildVisionPrompt`, and `buildVerbatimPrompt` in `PhotoToFlashcardsUseCase.ts` to prevent the three copies from drifting.

**Usage logging:** `logClaudeUsage(label, usage)` from `logClaudeUsage.ts` writes one `[claude-usage] label=… input=… output=… cache_create=… cache_read=…` line per Claude response to `console.info`. Every server-side Claude call site is responsible for calling it after the response (or `finalMessage` for streams) — labels: `ClaudeService`, `ChatUseCase`, `claudeFileConversion`, `AINoteTypeUseCase`, `OstController`. The helper is the single grep target for proving cache hit rate in prod. Missing or null cache fields render as `0`. Per `.claude/rules/security.md`, the log line carries no PII, secrets, or user content — just token counts.

**Partial chunk success (always on):** Both fan-out sites in `generateDeckInfo` go through the private `runChunks` helper, which always uses `Promise.allSettled` so a single chunk parse failure no longer kills the whole job — there is no env var controlling this. Succeeded chunks are merged as normal; failures are collected as `{ chunkIndex, reason }` and emitted via `console.info('[Claude] Some chunks failed; continuing with the rest', { failures, ok, total })`. If zero chunks succeed, the call throws using the first failure's reason — a deck is never returned empty. The `comprehensive`/`floor v1` path already tolerated per-chunk failures via `runWithSemaphore`. The return type of `generateDeckInfo` is `DeckInfo[]`; the dropped-chunk count is logged server-side but not yet surfaced to the user (deferred — would need a widened return shape threaded through `PrepareDeck` and the job result).

**Truncated chunk retry:** When a chunk's response carries `stop_reason === 'max_tokens'`, `generateDeckInfoFromChunk` throws `ClaudeTruncatedError` (carrying the chunk content) instead of parsing the truncated JSON. `runChunkWithTruncationRetry` wraps every per-chunk call: on `ClaudeTruncatedError` it splits the chunk in half via `splitChunkInHalf` (prefers a `</details>` boundary near the midpoint, falls back to the raw midpoint) and retries each half **once**. If a half still truncates, that `ClaudeTruncatedError` propagates to `runChunks`, which drops just that chunk (partial-success path) — the rest of the deck still ships. The retry is bounded to the detectable truncation signal only; `CHUNK_SIZE` and per-chunk `max_tokens` are unchanged, so the 99% of chunks that parse fine pay no extra cost. The split-retry log line is `[Claude] Retrying truncated chunk as halves` with `originalBytes` and `halfBytes`.

**Transient API retry:** `generateDeckInfoFromChunk` re-issues the Anthropic stream once (`MAX_CHUNK_API_ATTEMPTS = 2`, `CHUNK_RETRY_BASE_DELAY_MS = 500`) when the call fails with a transient error — `isTransientChunkError` returns true for a dropped/timed-out connection (`APIConnectionError` / `APIConnectionTimeoutError`, identified by `constructor.name` so it survives the SDK mock) or an `APIError` whose `status` is 408/409/429/529/5xx. The SDK auto-retries non-streaming timeouts, but a **stream that drops after it started** is not resumable and is not auto-retried — this loop covers that gap (the prod symptom was a chunk failing at ~91s with no retry). Non-transient errors (auth, validation, 4xx) throw on the first attempt. After the bounded retry is exhausted the error still propagates to `runChunks`, so the partial-success path is unchanged. The `[Claude] API request failed` log line carries `attempt` and `willRetry`.

**Comprehensive mode (per-user `CardOption`):** `generateDeckInfo` takes an optional 8th `options: GenerateDeckInfoOptions` parameter with `{ isPaying?: boolean; userId?: number | null; comprehensive?: boolean }`. When `options.comprehensive === true` **AND** `options.isPaying === true`, the default chunked path (not heading-driven) routes through `runFloorV1` instead of the bare `runChunks` fan-out. The gate is a per-user CardOption (`ai-comprehensive`, key on `CardOption.aiComprehensive`, default `false`) the user opts into from the Card options form — no server-flag, no env var. `runFloorV1` does four things on top of the default behavior: (a) caps parallel Claude calls at `FLOOR_V1_MAX_PARALLEL=4` via an in-process semaphore (`runWithSemaphore`); (b) stamps every returned card with `chunkIndex` (new optional field on `CardInfo`) for provenance; (c) runs up to `FLOOR_V1_MAX_TOPUP_ROUNDS=2` top-up rounds against the thinnest-quartile chunks (by card yield) whenever merged total card count is below `FLOOR_V1_CARD_FLOOR=200`, stopping early on zero net-new cards or when elapsed exceeds `FLOOR_V1_TOPUP_BUDGET_MS=50_000`; and (d) emits a single `ai_conversion_completed` analytics event per call with `{ card_count, chunks, top_up_rounds, cost_usd, elapsed_ms, comprehensive }`. The output is clamped to `FLOOR_V1_CARD_CEILING=500` cards across all decks. Top-up rounds re-issue chunks with `userInstructions` augmented by a "Do NOT repeat these fronts" preamble built from the first 80 already-collected fronts (`buildTopUpInstruction`). Cost is computed from per-chunk Anthropic `usage` totals at $3/$15 per million input/output tokens with a 0.1× cache-read discount and 1.25× cache-write premium (`FLOOR_V1_INPUT_TOKEN_PRICE_PER_MILLION`, `FLOOR_V1_OUTPUT_TOKEN_PRICE_PER_MILLION`, `FLOOR_V1_CACHE_READ_DISCOUNT`, `FLOOR_V1_CACHE_WRITE_PREMIUM`). `track` is loaded via lazy `require` inside the call site so importing this file does not pull in `data_layer/index.ts → knex` at module-load time (which broke `GeneratePackagesUseCase.test.ts`). The off path — comprehensive unset/false OR `isPaying !== true` — preserves today's behavior bit-for-bit (no semaphore, no top-up, no provenance stamp, no event). Heading-driven and partial-success paths are unaffected. The `comprehensive: true` field on the telemetry payload lets analytics compare opt-in vs default usage. The toggle is paid-tier-only in the UI; the server gate enforces the same constraint by ANDing `isPaying`.

## Heading-driven contract (`cardStyle: 'heading-driven'`)

`generateDeckInfo` accepts an optional fifth argument `cardStyle?: string`. When `cardStyle === 'heading-driven'`:

1. The stripped HTML is passed to `detect('html', strippedContent)` from `src/lib/cardStyle/headingDriven/detect.ts`, which returns a `Heading[]` — one entry per `h1`–`h6` tag.
2. If headings are found, `splitByHeadings(headings)` from `src/lib/cardStyle/headingDriven/splitByHeadings.ts` produces one `ChunkPayload` per leaf heading (deepest level present; headings with empty bodies are skipped).
3. Each chunk is sent to Claude as a separate `generateDeckInfoFromChunk` call with the card-style prompt fragment injected — "For each chunk, produce 2–6 cards. Each card's front references this chunk's heading; each card's back holds one fact." The fragment comes from `getCardStylePromptFragment.ts`.
4. If zero headings are detected, the pipeline logs `[Claude] heading-driven:fallback` and falls through to the default `chunkHtmlByDetails` path unchanged. No error is thrown.

**The mode is dormant until the picker UI (`#2616`) ships.** No caller currently passes `cardStyle: 'heading-driven'`; the default path is entirely unchanged when `cardStyle` is absent or any other value.

**Format support:** The `detect` dispatcher handles `'markdown'` (regex on `^#` lines) and `'html'`/`'notion-html'` (cheerio `h1`–`h6` traversal) via `detectMarkdown.ts` and `detectHtml.ts` respectively. Docx and Notion exports are already converted to HTML before reaching `generateDeckInfo`, so the `'html'` detector covers them. Slide images are out of scope for V1.

**Cost and latency:** Each detected heading becomes one Claude call. A document with 10 headings produces 10 parallel Claude calls instead of 1–2 default chunks. Latency is bounded by the slowest call (parallel dispatch). Token cost scales linearly with heading count. Prompt caching applies to the shared `SYSTEM_PROMPT` block.

## Field-mapping contract (`fieldMapping?: FieldMapping`)

`generateDeckInfo` accepts an optional seventh argument `fieldMapping?: FieldMapping` (exported type from `ClaudeService.ts`). When provided, `buildFieldMappingPromptFragment(fieldMapping)` produces a prompt section listing each field's name and the user's instruction for it. That section is appended to the user message Claude receives, after `userInstructions` and before `cardStyleFragment`. The model is asked to emit the named fields in each card's output.

**Backward compatibility:** the argument is optional. All existing call sites that omit it continue to receive the default `{ front, back }` behaviour — no change to output shape or downstream card construction.

**Type:** `FieldMapping = { templateName: string; fields: Array<{ name: string; instruction: string }> }`. Exported from `ClaudeService.ts`; the web client imports the same shape from `web/src/lib/cardFields/types.ts` (shared vocabulary so PR #2635 can converge without duplicating the definition).

**Where the value comes from:** `CardOptionsForm` renders a `FieldMappingPanel` (collapsible `<details>`) in the Templates section after the template picker. When the user picks a template, the panel is pre-populated from `fieldMappingDefaults.ts` (keyed by template name). The user's edits persist to the form state. On save/submit the mapping is JSON-serialised into the `field-mapping` key of the settings payload. `CardOption` parses `input['field-mapping']` via `parseFieldMapping()` and exposes it as `settings.fieldMapping`. `PrepareDeck.ts` threads it into every `generateDeckInfo` call for the Claude branch.

**Graceful degradation:** if `parseFieldMapping` receives malformed JSON or a structurally invalid object, it returns `undefined` and the conversion falls back to the default two-field shape. Missing or extra fields emitted by the model are logged as warnings by the caller (per spec open question 3); an extra field from the model is dropped, a missing field is left blank.

## Card-size suffix contract (`cardSize: 'short' | 'medium' | 'detailed'`)

`generateDeckInfo` accepts an optional sixth argument `cardSize?: string`. The value is normalized inside `getCardSizePromptSuffix` (from `cardSize.ts`) to one of `'short'`, `'medium'`, or `'detailed'` — anything else falls back to `'medium'`. The helper returns a short prompt suffix (`Card size: N facts per card, target ~Nc characters per answer`) that is appended to the user message Claude receives, alongside `cardStyle` and `userInstructions` if present.

**Where the value comes from:** the CardOptionsForm in `/card-options` exposes a Short/Medium/Detailed segmented control under "Card size" (`#card-size` anchor). The choice persists to localStorage under `card-size` and is sent to the server alongside the rest of the per-page or default settings payload. The CardOption parser reads `card-size` into `settings.cardSize`, which `PrepareDeck.ts` then threads into every `generateDeckInfo` call for the Claude branch.

**What it does not change:** nothing downstream enforces the requested size — `cardSize` is a steering signal for Claude, and since the post-parse splitter was removed (see above) whatever length Claude returns is what ships.
