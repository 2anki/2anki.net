# Claude lib — card generation contracts

The claude lib converts HTML content into Anki flashcards using the Anthropic API. Two mechanisms enforce the minimum-information principle:

**Prompt enforcement** (`SYSTEM_PROMPT` in `ClaudeService.ts`): Claude is instructed to produce one fact per card. Multi-fact paragraphs must be split into separate cards at extraction time. Tables of N rows produce N cards. Cloze cards are exempt (already single-fact by nature). Cloze deletions drawn from one list or enumeration go on ONE card as sequential `{{c1::}}…{{cN::}}` (#4104 — one note per list instead of one near-identical card per item; Anki still generates a sibling reveal per deletion, so the study flow is unchanged while edits happen once). The same guidance is appended to the `cloze` card-style fragment in `getCardStylePromptFragment.ts`. If `userInstructions` explicitly requests detailed or longer cards — or separate cards per list item — those instructions override these defaults.

**Card dedup keys on front AND back, not front alone.** `dedupeIdenticalCards` (inside `mergeDeckInfoArrays`, and on the vision path) drops a card only when a normalized front+back has already been seen — genuine duplicates, e.g. a chunk boundary re-emitting a card. It used to key on the normalized front alone, which silently dropped every card after the first whenever several shared a front: a table emitting one card per column from a single row (fronts collide on the row's key term, backs are the distinct facts) lost every column but the first — the "only the first few columns become cards" report (#3849). Dropping fewer cards is the safe direction: a surviving near-duplicate is visible and Anki dedupes identical notes on import, whereas a dropped column is content the user never sees. The normalizer strips markup and collapses case/whitespace on both fields, so `<p>Water</p>` and `Water` still count as the same card. `longAnswerPreservation.test.ts` and the `dedupeIdenticalCards` suite guard this.

**No post-parse splitter.** There used to be one (`splitOversizedCards.ts`): it broke any non-cloze answer over 600 plain-text characters into up to 3 fragments along sentence boundaries. It was removed because it was net-destructive. Every fragment reused the original card's front, so `dedupeIdenticalCards` (then `dedupeCardsByFront`, which keyed on the normalized front alone) — which runs inside `mergeDeckInfoArrays` — kept only the first and silently discarded the rest. A 1869-character answer reached the user as 594 characters; without the splitter the same card ships whole. The splitter also stripped the answer's HTML before splitting and clamped output at 3 fragments, so even working as designed it dropped formatting and anything past ~1800 characters. Card length is now governed by the prompt alone (see Prompt enforcement above and the card-size suffix), which is where the decision belongs. Do not reintroduce a post-parse splitter without making the fragments survive dedupe — `longAnswerPreservation.test.ts` guards this.

**Parse hardening:** `parseDeckResponse` applies two extraction steps before `JSON.parse`. First, a line-anchored fence regex (`/^```json\n?|^```\n?|```\s*$/gm`) strips code fences from line boundaries only — backticks inside JSON string values are never touched. Second, `extractJsonArray(text)` locates the first `[` and last `]` and returns the slice, so leading/trailing prose cannot prevent parsing. When `JSON.parse` fails, `tryRepairDeckArray` runs `escapeStrayControlChars` then `jsonrepair`: `escapeStrayControlChars` converts every C0 control char except `\t \n \r` (0x00-0x08, 0x0b, 0x0c, 0x0e-0x1f) into a `\uXXXX` escape. This matters because `jsonrepair` itself **throws** on a raw stray control char inside a string (the German-law-PDF prod failure: PDF text extraction injects BEL/VT/ESC/US bytes into card text, so both `JSON.parse` and the repairer died and the job failed with `claude_parse_failed`). German „quotes", literal newlines/tabs, and trailing prose are mostly handled by `jsonrepair` once the stray control chars are escaped — but an unescaped ASCII `"` closing a German „quote makes `jsonrepair` itself throw when the prose after it contains a colon, comma, or parenthesis (the recurring `jsonrepair-threw` prod shape, e.g. `das „Dreieck der Wissenschaft": <b>Campus</b>` — the `": ` mimics a key terminator). So when the first `jsonrepair` attempt throws, `repairAndParse` retries after `escapeUnterminatedInnerQuotes`, a string-state walker that escapes a closing `"` unless the next non-space token could legally follow a string end (`}`/`]`/end, or `:`/`,` followed by a valid JSON value start). When `JSON.parse` **and** the repair both fail and the response is not an empty-content refusal, `parseDeckResponse` throws `ClaudeLargeSectionError` (`.message === LARGE_SECTION_USER_MESSAGE`, `.name === 'ClaudeLargeSectionError'`, exported) — a large or multi-chunk response Claude answered in good faith but `jsonrepair` could not salvage (the recurring `jsonrepair-threw` prod shape). The user is told to convert a smaller part or split the page instead of seeing `claude_parse_failed`. `UploadService` classifies it as an expected user-input state and `jobFailureReasonFromError` returns its message, so the actionable text reaches the user on both the upload and the `performConversion` job paths. The narrower `ClaudeParseError` (`.message === 'claude_parse_failed'`, `.name === 'ClaudeParseError'`) now only fires when `JSON.parse` succeeds but yields valid JSON that is not a deck array. Note: `max_tokens` truncation never reaches this branch — `generateDeckInfoFromChunk` throws `ClaudeTruncatedError` before parsing (see Truncated chunk retry), so `stop_reason` is never `max_tokens` here. Either way the raw payload never appears in the thrown error. The redacted summary log (`[Claude] Failed to parse response as JSON`) uses `redactClaudePayload(text)` which emits `{ length, prefix (80 chars), sha256_prefix (12 hex) }`, plus `repairFailureReason` (from the exported `describeRepairFailure(toParse)` — `jsonrepair-threw` | `not-array` | `empty-array` | `no-usable-card` | `recoverable`) and `rawTail` (last 400 chars, so a `max_tokens` truncation shows its cut point even when the full-body dump is display-truncated). On unrecoverable failure a second line `[Claude] Unrecoverable parse failure — full response` logs the **full raw body** (`{ chunkIndex }` plus the raw string as its own console argument — `util.inspect` truncates strings nested in objects at 10k chars, which silently dropped most of the dump) so the next occurrence is reproducible — the body is study content, never API keys/tokens.

**Shape sanitization:** after a successful parse, `parseDeckResponse` runs the array through `sanitizeCompactDecks` instead of a blind `as CompactDeck[]` cast. Entries that are not objects with a `cards` array are dropped; cards whose `q` is missing, non-string, or blank are dropped individually (a card with no front is unusable, and `cheerio.load(undefined)` in `expandCompactDeckInfo` used to throw and fail the WHOLE chunk via `runFloorV1`'s per-chunk rejection — the 2026-07-26 `chunkIndex: 52` prod failure, issue #3850); `a` coerces to `''` when non-string, `tags`/`media` keep only string entries, a blank/missing deck name falls back to `Untitled deck`. Dropped counts log once per chunk as `[Claude] Dropped malformed entries from parsed response`. One malformed card now costs that card only, never its chunk.

**PDF-image-fallback bypass (multimodal path):** A PDF whose text layer is not machine-extractable falls back in `PrepareDeck.ts` to `convertPDFToImages`, producing HTML that is one `<img>` per page and zero text — indistinguishable from a genuinely blank screenshot to `isImageOnlyContent`, which wrongly rejected these dense-but-unextractable study PDFs before Claude's vision was ever tried (issue #3804). `PrepareDeck` now marks every `convertPDFToImages`-derived HTML with `imageFallback` and passes `options.pdfImageFallback = { mediaBaseDir: workspace.location }` to `generateDeckInfo`. When that option is set, `generateDeckInfo` **skips** `isImageOnlyContent` and delegates to `generateDeckInfoFromPdfImages` (in `generateDeckInfoFromPdfImages.ts`), which resolves each page's `<img src>` against the base dir (rejecting any path that escapes it, per CWE-22), reads the bytes, and sends each page to Claude's multimodal `messages.create` with `buildPdfPageVisionPrompt` — the same image-input shape `PhotoToFlashcardsUseCase` uses. Pages run at concurrency 4, each retrying once at a larger token budget on `max_tokens`. Cards are parsed with the shared `parseDeckResponse`, expanded via `expandCompactDeckInfo`, and merged with `mergeDeckInfoArrays` (both now exported). Each page's rendered image is bundled onto that page's own cards: `attachPageImageToCompactDecks` (exported) sets `media: [relPath]` and appends a back `<img>` in the worker, where the page↔image pairing is known — the `src` value is `escapeAttribute`-escaped so a filename containing `"` (valid on Unix) cannot break out of the attribute and inject markup (CWE-79); the raw `relPath` stays on `media` for lookup. `expandCompactDeckInfo` receives the resolved page paths as its media-file list so the reference resolves — the scanned page ships on the card, not only its extracted text. This is gated by `context.attachPageImages` (default `true`); `PrepareDeck` and the `UploadService` restart path set it from the `embed-images` CardOption, and when a user has images off the page image is omitted and reported through `PrepareDeck`'s `droppedImageCount`. The multimodal path deliberately ignores comprehensive/`cardStyle`/`cardSize`/`fieldMapping` (deferred to a tracking issue). A page that returns no cards is skipped, and a page whose vision call fails terminally is skipped the same way — the failure is caught inside the worker rather than rejecting the shared `Promise.all`, so one bad page on a 68-page scan no longer discards the 67 that converted. The page's error is re-thrown only when **every** page failed, which keeps an outage reported as an outage instead of as empty content. When every page yields zero cards (genuinely blank) it throws `EmptyContentError(EMPTY_CONTENT_UPLOAD_MESSAGE)` — upload-surface copy, since this path only ever runs for file uploads (same throw when zero page images resolve at all, e.g. the 1-page pairing bug of #4170) — so the blank-screenshot rejection now comes from Claude's own vision response, not a pre-call heuristic. The image-only fail-fast still fires normally for real image-only uploads (no `pdfImageFallback` flag). **Cost note:** one vision call per PDF page (2–30s each), so a rasterized-PDF conversion is materially more expensive than the text path; the fallback only triggers when text extraction already failed. The per-page prompt text block carries a `cache_control` breakpoint (#4188): the prefix (page image + prompt, well past the cache minimum) is written per page, and read back at 0.1× when the identical page is re-sent — the truncation retry (a larger `max_tokens` does not invalidate the cache) and job restarts within the TTL.

**Text-layer PDF embedded figures (the other half of the #3939 image story):** a text-shaped PDF converts through `convertPdfTextToHtml(Auto)`, which used to hand Claude text-only HTML — every embedded image was counted in `droppedImageCount` and lost. `PrepareDeck` now passes the converters a lazy `LoadPdfImages` loader (gated on the `embed-images` CardOption) that runs poppler's `pdfimages -png -p` via `lib/pdf/extractPdfImages` — spawned argv-only, page-attributed from the output filenames, size-floored at `MIN_PDF_IMAGE_BYTES` (4KB, drops bullet glyphs and rules) and capped at `MAX_PDF_IMAGES` (64). The loader is called only once the text path is committed, so scanned/DRM/over-split PDFs never pay for it, and a missing binary degrades to the old text-only behavior instead of failing the conversion. Extracted figures are injected as `<img>` into the first synthesized card of their source page (`PdfCard.pageIndex`, stamped by both synthesizers; figures from cardless pages append after the toggles) and returned as `images` files named `<pdfName>-images/<file>` — the `-images` suffix because the PDF itself is written to the workspace under its own name and a file and directory cannot share one. `PrepareDeck` folds them into `allFiles` (written to the workspace, available to the plain parser's `embedFile`) and unions them into the Claude media list per generating HTML file (`pdfFigureNamesByHtml`) — the prefix convention in `mediaFilesForHtmlFile` doesn't match the `-images` dir, so the union is explicit. `droppedImageCount` reports only the remainder (`painted − embedded`), keeping the downloads notice honest.

**Empty-content refusal classifier:** when the model returns prose instead of JSON because the page had no extractable text (layout-only Notion pages that are not image-only), `looksLikeEmptyContentExplanation(cleaned)` matches the refusal against `EMPTY_CONTENT_SIGNALS` and `parseDeckResponse` throws `EmptyContentError` (`.message === EMPTY_CONTENT_USER_MESSAGE`, `.name === 'EmptyContentError'` — the name survives the worker boundary, `UploadService` classifies it as an expected user-input state, and `jobFailureReasonFromError` returns the carried message, code `empty_content`) instead of the generic `ClaudeParseError`, so the user is told the page looks empty rather than seeing `claude_parse_failed`. The PDF-image fallback throws the same class with `EMPTY_CONTENT_UPLOAD_MESSAGE` — file-surface copy (scan/no-text-layer advice) instead of Notion advice. This `parseDeckResponse` site serves both Notion HTML and upload text-path HTML and keeps the Notion wording; making it surface-exact needs a `surface` option threaded through `generateDeckInfo` → `generateDeckInfoFromChunk` → `parseDeckResponse` (deliberately not done yet). The signal list covers both self-descriptions ("no actual content", "consists only of") and direct requests for input ("I need to see", "please provide the", "no content was provided") — the latter added after prod showed these refusals falling through to a generic error.

**Observability:** `parseDeckResponse` uses `extractJsonArray` to locate the array; trailing prose is stripped and logged as `[Claude] Trailing prose stripped` with `chunkIndex`, `strippedBytes`, and an 80-char sample — grep this to track model drift. Parse failures are logged as `[Claude] Failed to parse response as JSON` with `chunkIndex` and three redacted payload shapes (no raw content); the leading-indicator metric is the count of this log line in pm2 stderr.

**Override path:** `userInstructions` passed to `generateDeckInfo` flow into the prompt as an "Additional instructions" block. A user asking for "keep cards detailed" or similar will get the prompt's min-info rules deprioritised in Claude's output, and nothing downstream shortens the result.

**Tag normalization:** `normalizeTag(raw: string): string` (exported) converts a raw tag string from Claude's response into a safe Anki tag: lowercase, spaces→`_`, non-`[a-z0-9_]` characters stripped, capped at 32 characters. Called in `expandCompactDeckInfo` (Claude-text path) and in `buildDeckInfo` inside `PhotoToFlashcardsUseCase` (Photo-to-Deck path). Empty tags (e.g. all-punctuation input) are filtered out before the card is written. The `SYSTEM_PROMPT` already declares `"tags": string[]` in the schema; `expandCompactDeckInfo` now normalizes every tag the model emits and drops empty results.

**Math delimiter contract:** `ANKI_MATH_FRAGMENT` (exported from `ankiMathFragment.ts`) is a short instruction block injected into every Claude prompt that may produce math content. It instructs Claude to use `\(...\)` for inline math and `\[...\]` for display math, never `$...$` or `$$...$$`. Chemistry uses `\(\ce{...}\)` via mhchem. The fragment is shared across `SYSTEM_PROMPT` (exported from `ClaudeService.ts`), `buildVisionPrompt`, and `buildVerbatimPrompt` in `PhotoToFlashcardsUseCase.ts` to prevent the three copies from drifting.

**Usage recording:** `recordClaudeUsage({ surface, model, usage, userId?, requestId?, durationMs? })` from `recordClaudeUsage.ts` replaces the old `logClaudeUsage`. Per Claude response it (a) writes one `[claude-usage] surface=… model=… user=… request=… input=… output=… cache_create=… cache_read=… cost_usd=…` line to `console.info` (`user` renders `anon` when userId is null; `request=` is the `X-Request-Id` from `requestIdMiddleware` and is omitted when the call has no originating request — the #4198 correlation hook: the upload paths thread `res.locals.requestId` → `GeneratePackagesUseCase.execute` → `UploadGenerationTask.requestId` → `PrepareDeck` input → `GenerateDeckInfoOptions.requestId` → `SpendAttribution` on every chunk call, and the same id sits on the per-chunk `[Claude] Sending request / Received response / chunk done / truncated / API request failed` objects) (still the grep target for cache hit rate; missing cache fields render as `0`), and (b) fire-and-forget tracks an `ai_usage_recorded` event into the `events` table with `{ surface, model, cost_usd, duration_ms?, usage: { input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens } }` — token counts MUST stay nested under `usage` because `track()` strips any top-level prop key matching `/token/i` as PII. The track call is wrapped in try/catch so a missing event sink can never fail a conversion. Every server-side Claude call site calls it after the response (or `finalMessage` for streams) — surfaces: `conversion` (ClaudeService, per chunk), `chat`, `chat_tagging`, `file_conversion`, `note_type_ai`, `pdf_page_vision`, `photo_to_deck` (retry calls record separately — both bill). **Every surface passes `userId`** (since the 2026-08-16 spend spike, which was unattributable because the conversion path dropped it): the chunk path threads `GenerateDeckInfoOptions.userId` through `runFloorV1`/`generateDeckInfoFromChunk`, the vision path through `generateDeckInfoFromPdfImages`, `file_conversion` through `ConvertOptions.userId` from `PrepareDeck`'s `input.userId`, and `note_type_ai` from the controller's `getOwner(res)`. A new call site that records usage without a userId reintroduces the null bucket — don't. Cost comes from `pricing.ts` (`computeUsageCostUsd(model, usage)` / `resolveModelPricing`) — the single model-keyed price table (sonnet $3/$15, haiku $1/$5, cache read 0.1×, cache write 1.25×; unknown models price at sonnet rates); do not reintroduce per-file price constants. `/api/ops/ai-usage` aggregates the event for the ops System tab. Per `.claude/rules/security.md`, the log line carries no PII, secrets, or user content — just token counts.

**Partial chunk success (always on):** Both fan-out sites in `generateDeckInfo` go through the private `runChunks` helper, which always uses `Promise.allSettled` so a single chunk parse failure no longer kills the whole job — there is no env var controlling this. Succeeded chunks are merged as normal; failures are collected as `{ chunkIndex, reason }` and emitted via `console.info('[Claude] Some chunks failed; continuing with the rest', { failures, ok, total })`. If zero chunks succeed, the call throws using the first failure's reason — a deck is never returned empty. The `comprehensive`/`floor v1` path already tolerated per-chunk failures via `runWithSemaphore`. The return type of `generateDeckInfo` is `DeckInfo[]`; the dropped-chunk count is logged server-side but not yet surfaced to the user (deferred — would need a widened return shape threaded through `PrepareDeck` and the job result).

**Truncated chunk retry:** When a chunk's response carries `stop_reason === 'max_tokens'`, `generateDeckInfoFromChunk` throws `ClaudeTruncatedError` (carrying the chunk content) instead of parsing the truncated JSON. `runChunkWithTruncationRetry` wraps every per-chunk call: on `ClaudeTruncatedError` it splits the chunk in half via `splitChunkInHalf` (prefers a `</details>` boundary near the midpoint, falls back to the raw midpoint) and retries each half **once**. The halves settle independently: whichever halves parsed are kept, and the original `ClaudeTruncatedError` propagates to `runChunks` (which drops just that chunk, partial-success path) only when **every** half failed. Under the previous `Promise.all` a second truncation on one half discarded the cards its sibling had already produced — prod 2026-07-27 shipped 53 cards where 129 had parsed, silently. The partial-keep log line is `[Claude] Keeping the halves that parsed`. Per-chunk `max_tokens` is the flat `CHUNK_MAX_TOKENS` (32768) for every chunk; it used to scale with the chunk's own byte count, which let a truncated chunk's halves fall under the threshold and retry at half the budget the parent had already overrun. `max_tokens` is a cap rather than a charge, so the flat ceiling costs nothing. It was 16384 until 2026-08-16, when Sonnet 5's fuller answers hit that cap on 71% of conversion calls and every hit re-billed the chunk through this very retry (~3x cost, $57 of a $74 day) — the ceiling must stay comfortably above what the model wants for a `CHUNK_SIZE` chunk or the retry becomes the main cost driver. The split-retry log line is `[Claude] Retrying truncated chunk as halves` with `originalBytes` and `halfBytes`. **Chunk size is input-tiered (2026-08-21):** `chunkHtmlByDetails` uses `CHUNK_SIZE` (40k chars) normally, but an input past `GIANT_INPUT_THRESHOLD` (300k chars) chunks at `GIANT_INPUT_CHUNK_SIZE` (20k) from the start — a giant document fills any output cap (2026-08-17: 17 calls pegged at exactly 32768, each re-billed through the halving retry, $33.72/day vs a <$15 target), so starting at half size keeps answers under the cap instead of paying the retry to discover that. Normal documents chunk exactly as before; the tier keys on each call's own input length. Guarded by `chunkHtmlByDetails.test.ts`.

**Transient API retry:** `generateDeckInfoFromChunk` re-issues the Anthropic stream once (`MAX_CHUNK_API_ATTEMPTS = 2`, `CHUNK_RETRY_BASE_DELAY_MS = 500`) when the call fails with a transient error — `isTransientChunkError` returns true for a dropped/timed-out connection (`APIConnectionError` / `APIConnectionTimeoutError`, identified by `constructor.name` so it survives the SDK mock) or an `APIError` whose `status` is 408/409/429/529/5xx. The SDK auto-retries non-streaming timeouts, but a **stream that drops after it started** is not resumable and is not auto-retried — this loop covers that gap (the prod symptom was a chunk failing at ~91s with no retry). Non-transient errors (auth, validation, 4xx) throw on the first attempt. After the bounded retry is exhausted the error still propagates to `runChunks`, so the partial-success path is unchanged. The `[Claude] API request failed` log line carries `attempt` and `willRetry`.

**Comprehensive mode (per-user `CardOption`):** `generateDeckInfo` takes an optional 8th `options: GenerateDeckInfoOptions` parameter with `{ isPaying?: boolean; userId?: number | null; comprehensive?: boolean }`. When `options.comprehensive === true` **AND** `options.isPaying === true`, the default chunked path (not heading-driven) routes through `runFloorV1` instead of the bare `runChunks` fan-out. The gate is a per-user CardOption (`ai-comprehensive`, key on `CardOption.aiComprehensive`, default `false`) the user opts into from the Card options form — no server-flag, no env var. `runFloorV1` does four things on top of the default behavior: (a) caps parallel Claude calls at `FLOOR_V1_MAX_PARALLEL=4` via an in-process semaphore (`runWithSemaphore`); (b) stamps every returned card with `chunkIndex` (new optional field on `CardInfo`) for provenance; (c) runs up to `FLOOR_V1_MAX_TOPUP_ROUNDS=2` top-up rounds against the thinnest-quartile chunks (by card yield) whenever merged total card count is below the run's floor, stopping early on zero net-new cards or when elapsed exceeds `FLOOR_V1_TOPUP_BUDGET_MS=50_000`; and (d) emits a single `ai_conversion_completed` analytics event per call with `{ card_count, chunks, top_up_rounds, cost_usd, elapsed_ms, comprehensive }` plus `clamped_from` when the ceiling clamp fired. **Floor and ceiling scale with `cardSize`** via the exported `resolveFloorV1Bounds(cardSize)`: `short → {200, 500}`, `medium → {150, 400}` (the `validateCardSize` default), `detailed → {80, 250}` — so a `detailed` run targets fewer, fuller cards instead of being topped up back to micro-card counts (the rating-1 "too many tiny cards" feedback, spec `comprehensive-cardsize`). The ceiling clamp logs `[Claude] floor v1 ceiling clamp { preClampCount, ceiling }`; before this it silently dropped overflow (573→500 in the triggering prod case) with no log or metric. Top-up rounds re-issue chunks with `userInstructions` augmented by a "Do NOT repeat these fronts" preamble built from the first 80 already-collected fronts (`buildTopUpInstruction(existingFronts, cardSize)` — for `detailed` the lead sentence asks for 3-4-fact cards instead of "single-fact", so the top-up no longer fights the Card size directive). Cost is computed from per-chunk Anthropic `usage` totals via the shared price table in `pricing.ts` (`computeUsageCostUsd` — sonnet $3/$15 per million with a 0.1× cache-read discount and 1.25× cache-write premium). `track` is loaded via lazy `require` inside the call site so importing this file does not pull in `data_layer/index.ts → knex` at module-load time (which broke `GeneratePackagesUseCase.test.ts`). The off path — comprehensive unset/false OR `isPaying !== true` — preserves today's behavior bit-for-bit (no semaphore, no top-up, no provenance stamp, no event). Heading-driven and partial-success paths are unaffected. The `comprehensive: true` field on the telemetry payload lets analytics compare opt-in vs default usage. The toggle is paid-tier-only in the UI; the server gate enforces the same constraint by ANDing `isPaying`.

**Conversion result cache (#4213):** re-uploading an identical document re-billed the whole AI path; `generateDeckInfo` now wraps the text path in `withConversionResultCache` (`conversionResultCache.ts`) so an identical input returns the cached `DeckInfo[]` instead of another Claude call. The cache is content-addressed: `buildConversionCacheKey` is a SHA-256 over normalized content (CRLF→LF, trimmed) plus **every** output-affecting input — `mediaFiles`, `userInstructions`, `cardStyle`, `cardSize`, `fieldMapping`, `comprehensive`, `isPaying` (floor-v1 gates on both, so a free vs paid run differs), `CONVERSION_MODEL`, and `PROMPT_VERSION` (a digest of `SYSTEM_PROMPT`). Miss any one and the cache would serve wrong output, so a model swap or a `SYSTEM_PROMPT` edit changes the key and retires prior entries automatically — no manual bump, and it dovetails with the model-swap cost-envelope checklist. `CONVERSION_MODEL`/`PROMPT_VERSION` are exported from `ClaudeService.ts`; the model string is used both in the API call and the key so they can never drift. It is opt-in per call via `GenerateDeckInfoOptions.conversionResultCache` — `PrepareDeck` and the `UploadService` restart path pass `getConversionResultCache()`; when it or `DATABASE_URL` is absent the wrapper is skipped and behavior is bit-for-bit unchanged. **The vision/`pdfImageFallback` path is never cached** — it reads image bytes off disk that the key does not capture. Both cache read and write are wrapped so any cache-layer error logs and falls through to a fresh conversion — a broken cache never fails a conversion. Storage is the `conversion_result_cache` table (adapter `ConversionResultCacheRepository`, user-agnostic on purpose — two people converting the same file share one entry, no leak since the second supplied that content); a 30-day read-time ttl (`CONVERSION_CACHE_TTL_DAYS`) bounds growth, and `deleteOlderThan` exists for a future reaper (none wired). The cache-hit log line is `[Claude] conversion cache hit` with the key prefix only, never content.

**Cross-file dedup (multi-file AI uploads, #3918):** when one AI upload carries ≥2 content files, the files convert **sequentially** and the running front set threads into each later file's prompt, so the model does not re-emit the same fact worded three ways across a chapter + transcript + slides. The mechanism reuses the same "Do NOT repeat these fronts" preamble as the comprehensive top-up: `buildTopUpInstruction(fronts, cardSize)` and `collectExistingFronts(decks)` are **exported** (private, floor-v1-only before this) and composed with — never replacing — any caller `userInstructions` (append `\n\n`). The prompt caps the listed fronts at 80, but samples them **evenly across the whole accumulated list** (`sampleEvenly`, deterministic stride) rather than the first 80 — otherwise, once the earliest file alone produced 80+ fronts, every later file's hint froze to file 1 and the files in between went unrepresented. The front list is only a model hint; the safety net is a deterministic backstop: `absorbFileIntoCrossFileDedup(state, decks)` (exported) filters cards whose key matched an **earlier file** of the same upload, then absorbs this file's own keys afterward. The key is `cardDedupeKey(card)` — the exact same NUL-separated normalized front+back that `dedupeIdenticalCards` uses (shared helper, so they cannot drift; a space separator would collide boundary-shifted front/back splits and silently drop distinct cards). Filtering against the prior-file key set (not one that grows within the current file) preserves single-file semantics — `dedupeIdenticalCards` scopes per-deck, so a card legitimately repeated across two sub-decks of one file survives, and `cross_file_duplicates_suppressed` counts only genuine cross-file drops. `createCrossFileDedupState()` seeds an empty accumulator. The orchestration lives in two places because the two entry points route differently: **zip / Notion-export** delivers all files to one `PrepareDeck` call (the accumulator is created there — `ownsDedup` — when no state was threaded in and `htmlFiles.length >= 2`), while **loose multi-file** sync uploads process each file through its own `PrepareDeck` in the worker loop — there `doGenerationWork` creates one accumulator (gated by `shouldDedupeAcrossFiles`) and threads it via `DeckParserInput.crossFileDedup` into each file, **including zips** (through `getPackagesFromZip` → `buildClaudeFlashcardDeck`), so a mixed loose+zip upload dedupes across the container boundary and emits exactly one event. Each loose file keeps its own apkg — no packaging change. Per-file sub-deck names are preserved; a sub-deck emptied by dedup drops out. **A file whose cards were entirely covered by earlier files returns `undefined` from `PrepareDeck` (no exporter run)** — exporting an empty deck throws `PythonZeroCardsError`, and with no per-file catch in the worker loop that would fail the whole upload and discard the earlier files' good decks; returning no deck lets the earlier files carry the upload (`PrepareDeck` now returns `PrepareDeckResult | undefined`, and every caller already null-checks). **The gate** (`shouldDedupeAcrossFiles` → `countAiContentFiles` → `reachesClaudeContentPath`) mirrors the exact routing in `processFile`: it excludes files pre-empted by the AnkiApp/mindmap/Kindle/epub/xml branches (e.g. `My Clippings.txt` is a Kindle vocab file, not a Claude file) and includes image-quiz images and zips. Zips count as one container at the gate (their true content-file count is only known after extraction); the emitted `source_file_count` uses `filesProcessed`, the **actual** number of AI-converted content files across loose files and zip contents. **Analytics:** one upload-level `ai_conversion_completed` fires from whichever site owns the accumulator, carrying `{ source_file_count, cross_file_duplicates_suppressed }` — the same event name as the per-file floor-v1 event (no new `KNOWN_EVENTS` entry), distinguished by these props (the per-file rows carry `cost_usd`/`chunks`; the upload-level row carries the two cross-file props). Single-file uploads never create an accumulator and are bit-for-bit unchanged.

## Heading-driven contract (`cardStyle: 'heading-driven'`)

`generateDeckInfo` accepts an optional fifth argument `cardStyle?: string`. When `cardStyle === 'heading-driven'`:

**Section bodies are re-bounded before dispatch**: `splitByHeadings` is content-driven and unbounded, so a document whose whole body sits under one heading used to ship as a single chunk of hundreds of KB that could only truncate and cascade (the 2026-08-16 spend spike's worst single offender, a ~470KB one-section doc). The call site now runs each section body through `chunkHtmlByDetails`, so every dispatched chunk respects `CHUNK_SIZE` and repeats its section's anchor.

1. The stripped HTML is passed to `detect('html', strippedContent)` from `src/lib/cardStyle/headingDriven/detect.ts`, which returns a `Heading[]` — one entry per `h1`–`h6` tag.
2. If headings are found, `splitByHeadings(headings)` from `src/lib/cardStyle/headingDriven/splitByHeadings.ts` produces one `ChunkPayload` per leaf heading (deepest level present; headings with empty bodies are skipped).
3. Each chunk is sent to Claude as a separate `generateDeckInfoFromChunk` call with the card-style prompt fragment injected — "For each chunk, produce 2–6 cards. Each card's front references this chunk's heading; each card's back holds one fact." The fragment comes from `getCardStylePromptFragment.ts`.
4. If zero headings are detected, the pipeline logs `[Claude] heading-driven:fallback` and falls through to the default `chunkHtmlByDetails` path unchanged. No error is thrown.

**Reachability (audited 2026-08-17, wired same day):** the photo path accepts `heading-driven` from the request body via `PhotoToFlashcardsController`'s `ALLOWED_CARD_STYLES`. The TEXT path is now reachable end to end: the Card options form (`CardOptionsForm.tsx`) renders a Card style picker (the `card-style` setting) in the PDF & AI group that persists `card-style` to localStorage (the Templates group's visual note-type select was renamed to "Visual style" so the two no longer share a label), the upload form carries every localStorage key into the request body, and `CardOption` reads `input['card-style']` through `validateCardStylePicker`, which admits `cloze`, `qa`, and `heading-driven` (`VALID_PICKER_STYLES` in `getCardStylePromptFragment.ts`). The picker fires a `card_style_selected` usage event on change; a T+30 adoption review is due 2026-09-16. The 2026-05-23 changelog that advertised the picker is now true. The default path is unchanged when `cardStyle` is absent (the picker's Automatic option persists `''`, which coerces to the default).

**Format support:** The `detect` dispatcher handles `'markdown'` (regex on `^#` lines) and `'html'`/`'notion-html'` (cheerio `h1`–`h6` traversal) via `detectMarkdown.ts` and `detectHtml.ts` respectively. Docx and Notion exports are already converted to HTML before reaching `generateDeckInfo`, so the `'html'` detector covers them. Slide images are out of scope for V1.

**Cost and latency:** Each detected heading becomes one Claude call. A document with 10 headings produces 10 parallel Claude calls instead of 1–2 default chunks. Latency is bounded by the slowest call (parallel dispatch). Token cost scales linearly with heading count. Prompt caching note (#4188): `SYSTEM_PROMPT` alone (~600 tokens) is below Sonnet 5's 1024-token cache minimum, so a marker on it alone is silently ignored. `buildUserContentBlocks` therefore splits the user message into two text blocks — chunk content + media list (carrying the `cache_control` breakpoint; the hashed prefix = system + that block, always past the minimum) and the per-job trailing sections (instructions, field mapping, style, size) uncached — byte-identical to `buildUserMessage`'s single string when concatenated (asserted by test). Reads fire when the same chunk content is re-sent within the 5-minute TTL: floor/comprehensive top-up rounds, cross-file dedup passes, job restarts, duplicate re-uploads. Verify with the `cache_create`/`cache_read` fields on `[claude-usage]` lines.

Measured 2026-07-29 on prod, so nobody has to re-derive it: `SYSTEM_PROMPT` is **2077 chars ≈ 572 tokens**, and a probe using prod's own client and prompt returned `cache_create=0 cache_read=0` on two back-to-back calls, while the identical call shape with a ~4000-token system block cached normally (`cache_create=3960` then `cache_read=3960`). The block is roughly half the size it needs to be. Note that measuring this by slicing the template literal out of the source over-reads — the prompt embeds a backtick, so a naive scan to the next `` `; `` runs long and reports ~13k chars. Read it off the compiled `SYSTEM_PROMPT` export instead.

**Caching is not the cost lever here, so don't spend effort on it.** A typical chunk call is ~13k input / ~4-9k output; at $3/M input and $15/M output the output side is roughly two-thirds of the bill. Caching the 572-token system block would cut ~4% of input, so ~1% of total. The only caching with real upside is the comprehensive-mode top-up rounds, which re-send the same chunk body 1-2 extra times — putting the chunk in the cached prefix and the varying instruction after it would make those repeats cheap. That is worth revisiting only if top-up volume grows; the far bigger lever is fewer and shorter outputs, which is what `resolveFloorV1Bounds` already does for `detailed`.

## Field-mapping contract (`fieldMapping?: FieldMapping`)

`generateDeckInfo` accepts an optional seventh argument `fieldMapping?: FieldMapping` (exported type from `ClaudeService.ts`). When provided, `buildFieldMappingPromptFragment(fieldMapping)` produces a prompt section listing each field's name and the user's instruction for it. That section is appended to the user message Claude receives, after `userInstructions` and before `cardStyleFragment`. The model is asked to emit the named fields in each card's output.

**Backward compatibility:** the argument is optional. All existing call sites that omit it continue to receive the default `{ front, back }` behaviour — no change to output shape or downstream card construction.

**Type:** `FieldMapping = { templateName: string; fields: Array<{ name: string; instruction: string }> }`. Exported from `ClaudeService.ts`; the web client imports the same shape from `web/src/lib/cardFields/types.ts` (shared vocabulary so PR #2635 can converge without duplicating the definition).

**Where the value comes from:** `CardOptionsForm` renders a `FieldMappingPanel` (collapsible `<details>`) in the Templates section after the template picker. When the user picks a template, the panel is pre-populated from `fieldMappingDefaults.ts` (keyed by template name). The user's edits persist to the form state. On save/submit the mapping is JSON-serialised into the `field-mapping` key of the settings payload. `CardOption` parses `input['field-mapping']` via `parseFieldMapping()` and exposes it as `settings.fieldMapping`. `PrepareDeck.ts` threads it into every `generateDeckInfo` call for the Claude branch.

**Graceful degradation:** if `parseFieldMapping` receives malformed JSON or a structurally invalid object, it returns `undefined` and the conversion falls back to the default two-field shape. Missing or extra fields emitted by the model are logged as warnings by the caller (per spec open question 3); an extra field from the model is dropped, a missing field is left blank.

## Card-size suffix contract (`cardSize: 'short' | 'medium' | 'detailed'`)

`generateDeckInfo` accepts an optional sixth argument `cardSize?: string`. The value is normalized inside `getCardSizePromptSuffix` (from `cardSize.ts`) to one of `'short'`, `'medium'`, or `'detailed'` — anything else falls back to `'medium'`. The helper returns a short prompt suffix (`Card size: N facts per card, target ~Nc characters per answer`) that is appended to the user message Claude receives, alongside `cardStyle` and `userInstructions` if present.

**Where the value comes from:** the CardOptionsForm in `/card-options` exposes a Short/Medium/Detailed segmented control under "Card size" (`#card-size` anchor). The choice persists to localStorage under `card-size` and is sent to the server alongside the rest of the per-page or default settings payload. The CardOption parser reads `card-size` into `settings.cardSize`, which `PrepareDeck.ts` then threads into every `generateDeckInfo` call for the Claude branch.

**What it enforces:** since spec `comprehensive-cardsize`, the SYSTEM_PROMPT's min-info and density blocks explicitly defer to the Card size directive (before that, `detailed` was a one-line whisper the cached prompt's "one fact per card" and "maximum coverage" rules drowned out), and on the comprehensive path `resolveFloorV1Bounds(cardSize)` scales the floor/ceiling so the top-up loop cannot re-inflate a `detailed` run. There is still no post-parse enforcement — the splitter stays removed (see above); whatever length Claude returns is what ships.

## Chat invariants (moved from CLAUDE.md gotchas, 2026-07-17)

Chat has two non-obvious invariants. (1) An uploaded attachment's extracted text is persisted in `chat_messages.attachment_text` and replayed into model history (capped at 20k chars) so follow-up turns keep the document — before this, attachments were per-message only and the model would contradict itself ("I don't see any attachment") one turn later. (2) Each assistant turn downloads in ITS OWN note type, derived from that turn's card shapes (`effectiveTemplateForCards`), NOT the conversation-global selector — so an earlier MCQ turn exports as MCQ even when the pill sits on Basic. The template pill reflects the last turn's actual cards; if the AI overrode the requested type, re-selecting it forces a regenerate instead of a no-op. Deck-name on download is suggested from the AI's `Deck: <name>` line, else the conversation title.
