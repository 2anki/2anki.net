# Code-quality rules

Patterns the SonarCloud quality gate and review history have surfaced repeatedly.

| Requirement | Do instead | CWE |
| --- | --- | --- |
| Do not add comments to explain WHAT code does. | Rename the variable/function/file so the next reader doesn't need the comment. Comments are stripped before review. | — |
| Do not write `if (!ready) { … } else { … }`. | Lead with the positive: `if (ready) { … } else { … }` (Sonar S7735). Negation + else forces mental inversion. | — |
| Do not deduplicate code on the second occurrence. | Wait for the third. Premature abstraction is harder to undo than three honest copies. | — |
| Do not introduce `any`, `as any`, or `@ts-ignore` without a one-line justification on the same line. | Reach for a real type; if it is genuinely unknown, use `unknown` and narrow at the boundary. A justification is a comment on the same line with at least three words: after the `any` (`as any; // the SDK types omit this field`) or after `@ts-ignore` (`// @ts-ignore: Express does not type req.files`). `@ts-expect-error` is not flagged. Enforced by `pnpm debt` (part of `pnpm lint`, the CI `static` job and `/check`): oxlint (`.oxlintrc.debt.json`) finds every `any` and `@ts-ignore` in `src/` and `web/src/`, tests included, and the run fails when a file has more unjustified ones than `.debt-ratchet-baseline.json` lists for it (242 `any` and 5 `@ts-ignore` on 2026-11-24). An `eslint-disable` directive for the rule also silences it; don't use one to dodge the justification. | CWE-704 |
| Do not edit anything under `src/data_layer/public/`. | Run `pnpm dlx kanel -c ./.kanelrc.js` after migrations — those files regenerate. (Write/Edit to this path is blocked by `.claude/hooks/pre-write-secret-scan.py`.) | — |
| Do not add `console.log`, `debugger`, or `xdescribe` to code you touch. | Strip before pushing. The Stop hook nudges; review will block. Server logging uses `console.info`/`warn`/`error`/`debug`; those are allowed. Pre-existing `console.log` debt (99 calls on 2026-11-24) is baselined in `.debt-ratchet-baseline.json` and `debugger` has none; `pnpm debt` (part of `pnpm lint`, the CI `static` job and `/check`) fails when any file gains a `console.log` or `debugger`. No sweep is in scope. `xdescribe` stays on review. | CWE-489 |
| Do not skip layers (controller → repository, route → service). | Route → controller → use case → service → data layer. Each layer's CLAUDE.md says what belongs there. Enforced by `pnpm arch` (CI `static` job, `/check`): `no-layer-skip-to-data-layer` in `.dependency-cruiser.cjs` is an **error** over a known-violations baseline, `.dependency-cruiser-known-violations.json` (292 edges on 2026-11-24). Existing edges are ignored; a route or controller importing `src/data_layer/` anywhere else fails the build. | — |
| Do not grow a debt baseline (`.dependency-cruiser-known-violations.json`, `.debt-ratchet-baseline.json`) or regenerate one to admit a new violation. They list the debt that existed on 2026-11-24 and may only shrink; ceilings in `scripts/debt-ratchet/ratchet.test.ts` fail the suite if either grows. A moved or renamed file shows up as new debt under its new path: rename its entries to the new path in the same commit (the totals stay the same, so the ceilings still pass); that is the only hand edit allowed. | When you remove debt, the run still passes and prints a notice that the baseline can be lowered. Run `pnpm arch:shrink` or `pnpm debt:shrink` (both only remove or lower entries, never add), commit the smaller file, and lower the matching ceiling in `scripts/debt-ratchet/ratchet.test.ts`. | — |
| Do not put business logic in routes or controllers. | Controllers shape HTTP; use cases orchestrate; services hold reusable domain logic. | — |
| Do not import `knex` outside `src/data_layer/`. | Take a repository interface in the constructor; tests inject a fake. Enforced by `pnpm arch` (dependency-cruiser `no-knex-value-outside-datalayer`); use `import type { Knex }` for type-only needs. | — |
| Do not use chained nested ternaries. | Extract to a function with named branches. (oxlint's `no-nested-ternary` is configured as a warn, not an error — the lint passes with violations, so this rule is on you, not the build.) | — |
| Do not add a flag-on-flag option to a function (`opts.x`, `opts.skipX`, `opts.forceX`). | Two functions, or two call sites. Boolean parameter explosion is a code smell. | — |
| Do not catch an error only to rethrow the same error. | Drop the try/catch; let it propagate to `ErrorHandler`. | CWE-755 |
| Do not stack PRs (feature B branched off feature A's branch). | One PR per feature off `main`. The deploy pipeline ships a single branch. | — |
| Do not introduce backwards-compat shims, `_unused` renames, or "removed because…" comments for deleted code. | If the symbol is unused, delete it. The git history is the changelog. | — |
| Do not push changes that fail the local checks. | Before every push run the test files the diff touches, server typecheck and `arch`, web typecheck and lint, and `pnpm format:check`; run the full server suite and `/check` (the whole web suite) when the diff touches the shared parser or exporter list in `testing.md` or bumps a dependency (`dependencies.md`). CI runs both full suites on every push and is the gate. | — |
| Do not put `setInterval`/`setTimeout` for sync jobs at module top-level. | Schedule explicitly in `server.ts` startup or via a documented job runner. Stripe sync is **manual only**. | — |
| Do not gate a feature or runtime behavior behind a `process.env` flag (`*_ENABLED`, mode switches, behavior toggles, thresholds that change output) unless Alexander explicitly asked for that flag. Hidden flags silently change product behavior, rot undocumented, and default to the wrong thing — `CLAUDE_PARTIAL_SUCCESS_ENABLED` defaulted OFF and failed whole conversions for months while nobody knew it existed. | Make the correct behavior the unconditional default in code. If Alexander explicitly requests a flag: (1) the **unset default must be the safe/expected behavior** so a missing var never degrades the product, (2) test it with `=== 'true'` — never bare `if (process.env.X)`, which makes `X=false` truthy, (3) document it in `src/env.example` with its default and what each state does (a web-read flag needs a `web/.env.example`, which does not exist today — create it). | — |
| Do not use `localStorage` to persist user data, preferences, history, conversion results, or anything that should survive a session or be consistent across devices — unless explicitly asked to, or you are touching existing code that already uses `localStorage` for that purpose. | Store in the database with a proper Knex migration (`npx knex migrate:make <name> --knexfile ./src/KnexConfig.ts --migrations-directory ../migrations -x js`) followed by `pnpm dlx kanel -c ./.kanelrc.js`. `localStorage` is acceptable only for genuinely ephemeral UI state (collapsed panel, theme toggle) where the existing codebase already uses it. When in doubt, use the DB. | — |
| Do not send raw database rows, ORM objects, Knex query results, or untyped objects directly to the client via `res.json()`. | Map the result to an explicit typed response shape before sending. Internal structure leaking to the client is a coupling hazard and can expose schema details or sensitive fields. | CWE-209 |
| Do not ship a `fix:`/`feat:` changelog entry (or a PR titled as a fix) without a source change that actually implements it. A PR that adds only tests + a changelog claiming "X now works" is a false artifact — it tells users a bug was fixed when nothing changed. | If you investigated but could not land the fix, say so plainly in the PR body and **omit the changelog entry**. Tests that characterize a bug are fine as a `test:` PR, but must not assert the broken output as if it were correct, and must not carry a fix changelog. | — |
| Do not ship a new `/api/ops/<command>` POST route as backend-only. Every ops command needs a matching button in `web/src/pages/OpsPage/CommandsTab.tsx`; a route with no button is unusable without hand-crafting an authenticated curl call. This recurred twice (a 2026-07-23 command shipped invisible and needed a same-day follow-up; the 2026-08-17 audit found `send-pass-winback` buttonless), so the route↔button parity test beside `CommandsTab.tsx` now enforces it — if you add a command route and that test is not red, check the test's extraction rule. | Add the client fetch wrapper and the button+status-handling section in `CommandsTab.tsx` in the **same PR** as the route (mirror an adjacent command's shape). More generally: when a task says "mirror pattern X," find every layer X actually has (route, controller, use case, AND its UI trigger if one exists) before assuming the layer named in the task is the whole pattern. | — |
| Do not add a client analytics event to `web/src/lib/analytics/events.ts` without the identical string in `src/types/AnalyticsEvents.ts` in the same PR. A missing server entry does not error; it records `unknown: true` forever and silently undercounts. | `web/src/lib/analytics/events.parity.test.ts` asserts every web event exists server-side. If you add an event and it is not red, you did it right. Extend the event, not the test. | — |
